## Hash join GRACE — etapa N1, 23/11/2026

**O que foi construído:** `cbd/exec/hash_join.py` fornece `hash_join` e
`hash_join_cost`. A primeira função emite pares; a segunda estima blocos sem
ler registros. `tests/test_hash_join.py` usa dublês da camada de baixo.

**Raciocínio:** escolher o construtor pelo menor arquivo; tentar execução direta
quando ele cabe; caso contrário, aplicar o mesmo hash nos dois lados para que
chaves iguais caiam no mesmo par de partições. Construir a tabela de busca inteira
daquela partição antes de emitir resultados. Se ela não couber, repetir com outra
seed; após três níveis, usar lotes pequenos e varrer o outro lado para cada lote.

- **Construtor (build):** lado cujos registros ficam na tabela de busca em memória.
- **Sondagem (probe):** lado percorrido para procurar pares nessa tabela de busca.
- **Partição:** arquivo temporário com registros escolhidos pelo resultado do hash.
- **Seed:** número que muda a função determinística de distribuição entre níveis.
- **Skew:** distribuição desigual; no extremo, todas as linhas têm a mesma chave.
- **Reserva WORK:** páginas retiradas do buffer para representar os registros
  retidos pelo operador; temporários só usam as páginas restantes.
- **Multiconjunto:** coleção que preserva quantas vezes cada tupla aparece. Testar
  apenas um conjunto esconderia duplicatas faltando ou sobrando.

**Em palavras simples:** se a caixa pequena cabe na bancada, organize-a ali e
procure nela os itens correspondentes da outra caixa. Se não cabe, distribua as
duas por etiquetas, usando a mesma regra. A caixa da etiqueta 7 só precisa ser
comparada com a outra caixa da etiqueta 7. Se todas as etiquetas são iguais,
dividir de novo não ajuda: trabalhe com pequenos lotes e repasse a outra caixa.

**Custos e trade-offs:** SKS §15.5.5 é a referência indicada pelo guia. Execução
direta custa aproximadamente b_r+b_s; uma rodada GRACE, 3(b_r+b_s), porque lê,
grava e relê os dois lados. O modelo do guia acrescenta 4n de arredondamento.
Com M=64, curso=2 blocos e aluno=1.962, a execução direta estima 1.964
transferências. Com aluno=1.962 e inscricao=4.588, uma rodada com 38 partições
estima 3×6.550+4×38=19.802. São cálculos, não resultados medidos.
Mais partições podem evitar recursão, mas criam mais arquivos parcialmente
cheios. Limitar a recursão garante término; cair no laço pode custar mais leituras.
Cache e skew fazem o resultado real divergir. E&N: capítulo de processamento de
consultas, sem subseção/edição conferida nesta sessão (PDFs locais indisponíveis).

**Perguntas que o professor pode fazer:**

1. Por que não usar `hash()` do Python para escolher a partição?
2. Por que não emitir pares enquanto ainda está carregando o construtor?
3. Trocar a seed resolve uma partição com uma única chave repetida?

**Respostas:** 1. O hash de strings do Python pode mudar entre processos; usamos
`hash_value` para ter distribuição reproduzível. 2. Se o construtor exceder o
limite depois, o par terá de ser repartido e reiniciado: emitir antes poderia
duplicar a saída. 3. Não; chaves iguais precisam continuar juntas em qualquer
hash correto para o join. O laço em blocos termina sem exceder o lote reservado.

## Defeito de referência entre lotes — R-P5-01

**O que aconteceu:** a primeira versão limpava a lista do lote, mas a variável
`match` do `for` ainda apontava para o último registro. Na próxima sondagem,
estavam vivos os dois registros novos mais um antigo. O teste gerou tuplas sob
demanda e contou objetos vivos: versão bruta [2,3,3]; corrigida [2,2,2]. Ambas
emitiam o mesmo resultado, mostrando que resultado correto não prova memória
correta. A correção libera essa referência antes de carregar o próximo lote.

**Em palavras simples:** esvaziar a caixa não basta se alguém continua segurando
um dos objetos fora dela. É preciso soltar também esse objeto antes de trazer a
próxima caixa. A contagem dos objetos vivos detecta o que um teste só de saída
não percebe.

**Perguntas de fixação:**

1. `lista.clear()` elimina todas as referências aos elementos?
2. Por que a versão com defeito ainda devolvia a resposta certa?

**Respostas:** 1. Elimina as referências da lista; outras variáveis podem continuar
retendo os objetos. 2. A referência antiga não participava de outra comparação;
o problema era ocupar memória além do orçamento, não formar um par errado.

## Vazio e arquivo esparso — D-P5-05/06, R-P5-03/04/05

**O que foi corrigido:** o plano agora reconhece zero registros, e tanto operador
como custo retornam sem leitura. Isso vale mesmo quando o arquivo mantém blocos
alocados. Para entrada não vazia com bfr positivo menor que um, o lote N1 admite
no mínimo um registro por página reservada.

**Raciocínio e trade-offs:** n_blocks mede páginas ocupadas, não a existência de
linhas. n_records é o dado apropriado para reconhecer vazio, mas precisa estar
atualizado. bfr é a média de registros por bloco: 0,5 pode significar uma linha
em dois blocos esparsos. Não significa que a linha ocupa dois blocos: em blocagem
não estendida, um registro aceito pelo armazenamento cabe numa página. Por isso
o teto lógico usa floor((M−2)×max(1,bfr)). É uma correção conservadora para arquivo
esparso; a imprecisão para tamanhos variáveis ainda exige validação física.

**Em palavras simples:** uma caixa vazia ainda pode estar guardada no armário.
E uma caixa a cada dois espaços não significa que cada caixa ocupe dois espaços.
Não confunda espaço reservado com quantidade de objetos ou tamanho de cada um.

**Ligação com a teoria:** relação vazia não tem pares no join; seu plano custa
zero transferências se a cardinalidade é conhecida. A regra de um registro por
página vem da blocagem não estendida da arquitetura §2, enquanto a fórmula do
GRACE continua a do SKS §15.5.5 para relações não vazias.

**Perguntas de fixação:**

1. n_blocks=1 e n_records=0 são incompatíveis?
2. bfr=0,5 prova que um registro ocupa dois blocos?
3. O custo pode prever 123 transferências quando o plano não lê nada?

**Respostas:** 1. Não: o bloco pode continuar alocado após remoções. 2. Não: é
uma média de ocupação, não o tamanho de uma linha. 3. Nesse caso é defeito do
modelo; a correção usa o mesmo plano vazio no operador e no custo, que retorna 0.

## Compatibilidade do hash primário — D-P5-07, 24/11

Dois arquivos usam divisórias equivalentes quando têm o mesmo N (quantidade de
buckets), a mesma seed e o mesmo tipo de chave. Nesse caso, chaves iguais caem
no mesmo número de bucket. Se N ou seed diferirem, esse número pode mudar.
Enzo escolheu seguir a #65: depois dos atalhos vazio/direto, repartir ambos por
GRACE comum, em vez de aproveitar um hash e converter o outro para sua regra.

**Em palavras simples:** duas estantes numeradas de zero a nove não têm
necessariamente as mesmas caixas em cada prateleira. A numeração só ajuda a
compará-las diretamente quando a regra usada para guardar cada caixa é igual.

**Perguntas de fixação:**

1. N igual com seed diferente basta para usar bucket-join?
2. Aproveitar só um dos hashes incompatíveis seria sempre incorreto?

**Respostas:** 1. Não; a função pode enviar a mesma chave a buckets diferentes.
2. Não: há uma alternativa correta alinhando o outro lado pelo bucket_of do hash
escolhido. Ela foi preterida para seguir o aceite atual da issue; a economia de
I/O potencial fica documentada, e ainda não foi medida.
